# TCP Transport 生产化问题清单

## 文档目的

当前 TCP Transport 已具备客户端连接、服务器监听、异步收发、长度前缀分帧和统一网络事件等基础能力，可用于验证传输层抽象及小规模原型。

本清单记录其作为大型游戏项目底层传输方案前需要解决的问题。清单中的“完成标准”用于后续设计、实现和测试验收，不表示必须一次性完成所有工作。

## 1. 内存分配与 GC 压力

### 当前问题

发送时复制消息数组，接收时为每条消息创建新数组，发送消息头也会重复创建小数组。高频网络同步会产生大量短生命周期对象，并可能导致 Unity 主线程出现 GC 峰值。

### 解决方向

- 使用 `ArrayPool<byte>` 或包内自定义缓冲池。
- 每个连接复用固定大小的收发消息头缓冲区。
- 发送队列保存“缓冲区 + 有效长度”，发送结束或丢弃时归还缓冲区。
- 接收缓冲区通过具有明确释放语义的所有权对象交给事件消费者。
- 统计池命中率、租用字节数和未归还缓冲区数量。

### 完成标准

- 稳态收发路径不存在每包固定数组分配，无法避免的分配有明确记录。
- 发送成功、发送失败、连接关闭和队列清空路径均会归还缓冲区。
- 压力测试中不存在缓冲区泄漏，GC 分配量满足项目预算。

## 2. 事件队列缺少背压

### 当前问题

网络线程可以持续向事件队列写入，而游戏线程的消费速度可能更慢。无界队列会导致内存持续增长；简单丢弃事件又可能丢失连接关闭等关键状态。

### 解决方向

- 同时限制事件数量和事件负载总字节数。
- 区分不可丢弃的控制事件与可合并、可丢弃的数据事件。
- 当消费者持续落后时暂停对应连接读取，利用 TCP 流量控制向远端施加背压。
- 为主线程事件处理设置单帧数量或时间预算，但不能因此无限积压。
- 明确队列超限策略：暂停读取、拒绝新连接或关闭产生过量数据的连接。

### 完成标准

- 主线程停止消费时，进程内存不会无限增长。
- `ConnectionClosed` 等关键事件不会被静默丢弃。
- 队列积压和背压状态可被监控。

## 3. 连接数量限制存在并发竞争

### 当前问题

先读取字典 `Count`、再调用 `TryAdd` 不是原子操作。多个线程同时创建或接入连接时可能突破最大连接数。

### 解决方向

- 使用 `Interlocked` 原子计数或连接名额信号量预留槽位。
- 主动连接和服务端接入必须共享同一个名额管理器。
- 注册失败、连接关闭和异常退出时必须且只能释放一次名额。
- 达到上限属于可预期结果，应返回明确结果而不是依赖通用异常。

### 完成标准

- 高并发接入测试中，活动连接数永远不超过配置上限。
- 不存在重复释放、名额泄漏或负数计数。

## 4. 发送队列限制存在并发竞争

### 当前问题

检查队列计数和递增计数不是一个原子操作，并发调用 `Send` 时可能突破限制。仅限制消息条数也无法准确控制内存，因为消息大小不同。

### 解决方向

- 原子预留发送条目和发送字节额度。
- 同时配置最大待发送消息数与最大待发送字节数。
- 发送完成、发送失败和连接关闭清队列时准确释放额度。
- 定义 `SendQueueFull` 后的上层策略，避免无限重试形成忙循环。

### 完成标准

- 并发发送时队列条目数和字节数均不超过上限。
- 所有退出路径最终将计数恢复到正确值。

## 5. 初始化存在并发窗口

### 当前问题

Transport 可能先把状态发布为 `Running`，随后才写入配置。其他线程可能观察到 `Running`，但读取到尚未初始化的配置。

### 解决方向

- 使用 `Created → Initializing → Running` 状态转换。
- 完成配置校验并建立不可变配置快照后，最后通过 `Volatile.Write` 发布 `Running`。
- 明确重复初始化、初始化失败和未初始化关闭的行为。

### 完成标准

- 任何线程观察到 `Running` 时，所有运行所需字段都已经可见且不可变。
- 并发初始化最多只有一个调用成功。

## 6. 连接过程缺少超时与取消

### 当前问题

连接请求可能长时间停留在 `Connecting`，且 DNS 返回多个地址后没有统一的尝试、超时和回退策略。

### 解决方向

- 为单次连接尝试设置超时和 `CancellationToken`。
- 定义多个 `IPEndPoint` 的尝试顺序及 IPv6/IPv4 回退策略。
- 区分用户取消、连接超时、拒绝连接和网络不可达。
- 重连退避属于上层连接管理策略，不放入 TCP Transport。

### 完成标准

- 每次连接尝试都能在配置时间内成功、失败或取消。
- 连接中调用 `Close` 不会泄漏 Socket、任务或事件。

## 7. 缺少接收超时与慢速连接防护

### 当前问题

客户端可以声明一个合法长度后极慢地发送消息体，从而长期占用连接、缓冲区和任务。仅限制最大包长不能防止慢速连接攻击。

### 解决方向

- 分别设置消息头读取超时、消息体读取超时和连接空闲超时。
- 限制每连接每秒消息数和接收字节数。
- 未认证连接设置更严格的握手及认证时限。
- 超时和限流触发后使用稳定的断开原因关闭连接。

### 完成标准

- 慢速发送、半包停滞和空闲连接都会在规定时间释放资源。
- 正常高延迟网络不会因过严阈值产生不可接受的误断开。

## 8. 传输帧协议过于简单

### 当前问题

当前传输帧只有四字节负载长度，不能快速识别错误协议、版本不兼容或未来扩展能力。

### 解决方向

- 评估加入协议标识、协议版本、标志位和负载长度。
- 明确消息类型属于传输帧还是上层消息协议，避免职责重复。
- 对所有长度、标志和保留位进行严格验证。
- 保持网络字节序和跨平台一致性。

### 完成标准

- 非法或不兼容帧能够被确定地拒绝。
- 帧格式有版本化文档和兼容策略。
- 解析器通过边界值及模糊测试。

## 9. 接收数据所有权不明确

### 当前问题

`NetworkEvent.Payload` 使用 `ArraySegment<byte>`，但接口没有完整规定底层数组由谁持有、有效到何时以及谁负责释放。引入缓冲池后，这会直接导致数据覆盖或内存泄漏。

### 解决方向

- 使用可释放的负载所有权对象，例如 `NetworkPayload : IDisposable`。
- 或规定事件调度器处理完成后统一归还，业务处理器不得跨回调保存引用。
- 如果允许业务层长期保存数据，必须显式复制或转移所有权。
- 对重复释放提供安全保护和诊断。

### 完成标准

- API 文档能够明确回答“谁拥有、何时失效、谁归还”。
- 缓冲区不会在消费者使用期间被池重新租用。
- 忘记释放可以被测试或诊断工具发现。

## 10. 关闭流程不完整

### 当前问题

当前关闭流程偏向立即终止，会丢弃待发送数据，并且需要进一步验证正在连接、正在收发和重复关闭等并发场景。

### 解决方向

- 区分立即终止 `Abort` 和尝试清空发送队列的优雅关闭 `Close`。
- 明确关闭超时，避免优雅关闭无限等待。
- 保证一个连接只发布一次最终关闭事件。
- 明确本地主动关闭、远端关闭、连接重置、踢出和服务器停机的原因映射。
- 关闭后归还全部缓冲区、连接名额和异步资源。

### 完成标准

- 所有状态下调用关闭均为幂等操作。
- 不发生重复事件、资源泄漏或关闭后继续收发。
- 优雅关闭和立即终止都有确定的行为及测试。

## 11. 异常分类不稳定

### 当前问题

直接向上层暴露平台错误码和异常消息，会导致不同操作系统的行为不一致，业务层也难以制定稳定策略。

### 解决方向

- 定义稳定的网络错误类别，例如连接拒绝、连接超时、连接重置、地址占用、网络不可达、取消和协议违规。
- 保留原始平台错误码及异常作为诊断信息，但业务逻辑只依赖稳定类别。
- 规定哪些错误一定伴随连接关闭，哪些错误可以恢复。

### 完成标准

- Windows、Linux及目标游戏平台对相同问题产生相同的上层错误类别。
- 日志仍可查看原始错误信息用于定位。

## 12. TCP 不适用于全部实时数据

### 当前约束

TCP 具有可靠、有序传输和队头阻塞特性。前序数据丢失时，后续已到达数据也不能立即交付应用层，因此不适合所有高频实时状态。

### 架构要求

- TCP 用于登录、聊天、背包、房间和必须可靠有序的业务。
- 高频位置、朝向、输入和状态快照评估使用 UDP 或可靠 UDP。
- HTTP 独立为请求—响应模块，不强行适配 `IConnection`。
- 上层协议不能错误假设不同 Transport 具有相同语义。

### 完成标准

- 每类游戏消息都有明确的传输协议选择依据。
- TCP 队头阻塞不会成为核心实时玩法的单点限制。

## 13. 缺少生产诊断能力

### 当前问题

缺少连接、流量、队列、延迟和断开原因等指标，发生卡顿、断线或内存上涨时难以定位。

### 解决方向

- 统计活动连接数、连接建立耗时和连接失败原因。
- 统计每秒收发消息数及字节数。
- 统计发送队列和事件队列的数量、字节数及峰值。
- 统计协议错误、超时和各类断开原因。
- 日志携带 Transport、Listener、Connection 和会话关联标识。
- 允许关闭高成本诊断，避免正式环境过度开销。

### 完成标准

- 能够仅通过指标和日志定位连接积压、流量异常、慢消费者及主要断开原因。
- 诊断系统本身有明确性能预算。

## 14. 测试覆盖不足

### 当前问题

现有验证只覆盖基础本机回环流程，尚未覆盖并发、异常、攻击输入、长时间运行和跨平台差异。

### 解决方向

- 单元测试：状态机、帧编解码、计数器、错误映射和缓冲区所有权。
- 集成测试：连接、双向收发、连续消息、粘包、分片、半包断线和重复关闭。
- 并发测试：大量客户端同时连接、发送和关闭。
- 边界测试：空包、最大包、超长包、非法长度和随机输入。
- 故障测试：连接重置、网络中断、慢速发送、队列饱和和服务器停机。
- 长稳测试：持续运行并检查内存、任务、Socket和池缓冲区泄漏。
- 跨平台测试：Windows、Linux服务器及项目支持的客户端平台。

### 完成标准

- 核心状态和异常路径均有自动化测试。
- 压力测试达到项目定义的连接数、吞吐量和延迟目标。
- 长稳测试期间资源使用保持稳定。

## 建议实施顺序

第一阶段先保证并发和资源安全：

1. 修复初始化、连接名额和发送队列的原子性。
2. 定义 Payload 所有权并引入缓冲池。
3. 建立事件队列背压。
4. 完成连接、读取和空闲超时。

第二阶段完善协议和生命周期：

1. 完善帧协议及错误分类。
2. 区分优雅关闭和立即终止。
3. 增加限流与慢速连接防护。

第三阶段达到可运营标准：

1. 添加指标、日志和诊断接口。
2. 建立并发、故障、模糊、长稳和跨平台测试。
3. 根据真实游戏消息划分 TCP、UDP和可靠 UDP 的使用边界。

## 生产准入结论

只有在 P0 项目完成、压力目标明确并且自动化测试通过后，TCP Transport 才能进入大型游戏项目的正式网络链路。在此之前，它应被视为传输层原型和功能验证实现。
