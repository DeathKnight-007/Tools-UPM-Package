# SerializableReadWrite 知识点总结

## 1. Stream、FileStream 与资源管理

### 1.1 Stream

`Stream` 是 .NET 中顺序读写字节的抽象。文件流、内存流和加密流都继承自它，因此上层可以使用统一的读写方式处理不同数据来源。

常用成员：

- `Read`：从流的当前位置读取字节，并返回实际读取的数量。
- `Write`：从指定缓冲区向流写入字节。
- `Position`：当前读写位置。
- `Length`：流的总长度。
- `Seek`：相对于开头、当前位置或末尾移动读写位置。
- `Flush`：把缓冲区中尚未提交的数据写到底层资源。
- `CanRead`、`CanWrite`、`CanSeek`：表示流支持的操作。

每次成功调用 `Read` 或 `Write` 后，流的位置会自动向后移动。需要重复读取或修改文件前部内容时，必须通过 `Seek` 或 `Position` 重新定位。

```csharp
stream.Seek(offset, SeekOrigin.Begin);
stream.Position = 0;
```

`Stream.Read` 不保证一次填满请求的缓冲区。读取固定长度的文件头时，应循环读取，直到取得全部数据或流提前结束：

```csharp
private static void ReadExactly(Stream stream, byte[] buffer, int offset, int count)
{
    while (count > 0)
    {
        int readCount = stream.Read(buffer, offset, count);

        if (readCount == 0)
            throw new EndOfStreamException("文件提前结束");

        offset += readCount;
        count -= readCount;
    }
}
```

哈希算法的流式接口通常从流的当前位置处理到末尾，并不会自动从文件开头开始。计算哈希前必须确认当前位置正确。

### 1.2 FileStream

`FileStream` 是面向文件系统的 `Stream` 实现，只处理字节，不负责文本编码或对象序列化。

```csharp
using FileStream stream = new FileStream(
    path,
    FileMode.Create,
    FileAccess.ReadWrite,
    FileShare.None,
    64 * 1024);
```

构造参数的作用：

- `FileMode.Create`：创建新文件或清空并覆盖已有文件。
- `FileMode.Open`：打开一个已经存在的文件，不存在时抛出异常。
- `FileAccess.Read`：只允许读取。
- `FileAccess.Write`：只允许写入。
- `FileAccess.ReadWrite`：允许读写。
- `FileShare.None`：当前流存活期间不允许其他进程共享文件。
- `FileShare.Read`：允许其他进程同时读取。
- 缓冲区大小用于减少底层 I/O 调用次数，本包使用 64 KiB。

保存文件时使用 `FileMode.Create` 会直接覆盖原文件。输入路径和输出路径不能指向同一个文件，否则创建输出文件时可能先把输入内容清空。

比较路径时，应先转换成绝对路径：

```csharp
string source = Path.GetFullPath(sourcePath);
string output = Path.GetFullPath(outputPath);
```

### 1.3 流式处理与内存占用

`Stream.CopyTo` 会分块复制数据，不需要把整个文件一次性读入内存：

```csharp
inputStream.CopyTo(outputStream, 64 * 1024);
```

流式处理适合大文件，其内存占用通常与缓冲区大小相关，而不是与文件总大小相关。

以下操作会把完整数据保存在内存中：

```csharp
using var memoryStream = new MemoryStream();
inputStream.CopyTo(memoryStream);
byte[] data = memoryStream.ToArray();
```

`MemoryStream.ToArray()` 会创建一个新的完整数组。文件较大时会带来较高的内存峰值，大数组还可能进入 Large Object Heap，增加 GC 压力。因此只有确实需要完整 `byte[]` 时才应使用这种方式。

### 1.4 流的包装

一个流可以包装另一个流，在保留原有读写能力的同时增加新功能：

- `CryptoStream`：在读写过程中自动加密或解密。
- `StreamReader`/`StreamWriter`：在字节流与字符之间进行编码转换。
- 自定义 `ProgressStream`：转发读写操作并统计已处理字节数。

这是装饰器模式。包装流通常需要把以下成员转发给内部流：

```csharp
public override bool CanRead => innerStream.CanRead;
public override bool CanWrite => innerStream.CanWrite;
public override bool CanSeek => innerStream.CanSeek;
public override long Length => innerStream.Length;
```

统计读取进度时应使用 `Read` 实际返回的字节数，而不是请求读取的字节数：

```csharp
int readCount = innerStream.Read(buffer, offset, count);
onRead?.Invoke(readCount);
```

### 1.5 IDisposable 与 using

文件流、加密流和密码学对象都持有需要释放的资源。`using` 会在作用域结束时调用 `Dispose`，即使中途抛出异常也能释放资源：

```csharp
using FileStream inputStream = new FileStream(...);
using CryptoStream cryptoStream = new CryptoStream(...);
```

及时释放资源可以：

- 关闭文件句柄。
- 解除文件占用。
- 刷新缓冲数据。
- 释放密码学算法持有的资源。
- 确保 `CryptoStream` 写完最后一个加密分组和 Padding。

### 1.6 流的所有权与 leaveOpen

包装流默认可能在自身释放时关闭底层流。如果底层流仍由外部代码管理，应使用 `leaveOpen: true`：

```csharp
using var writer = new StreamWriter(
    stream,
    new UTF8Encoding(false),
    16 * 1024,
    leaveOpen: true);
```

所有权原则：

- 谁创建资源，通常由谁负责释放。
- 接收外部流的方法不应擅自关闭该流，除非 API 明确约定转移所有权。
- 包装流不拥有底层流时使用 `leaveOpen: true`。
- `Flush` 只刷新数据，不等同于释放资源。
- 不要同时让多个对象负责释放同一个流，以免出现提前关闭或重复使用已释放对象的问题。

## 2. AES、PBKDF2、SHA-256、HMAC-SHA256

### 2.1 AES 对称加密

AES 是对称加密算法，加密和解密使用同一把密钥：

```text
明文 + Key + IV -> AES 加密 -> 密文
密文 + Key + IV -> AES 解密 -> 明文
```

AES 主要提供机密性，使不知道密钥的人无法直接读取内容。AES 本身不等于完整性校验，密文是否被修改应通过 HMAC 等认证机制判断。

本包使用：

```csharp
using Aes aes = Aes.Create();
```

加密时使用 `CryptoStream`，上层只需不断写入明文，`CryptoStream` 会把密文写入底层文件流：

```csharp
using var cryptoStream = new CryptoStream(
    fileStream,
    aes.CreateEncryptor(),
    CryptoStreamMode.Write,
    leaveOpen: true);
```

解密时则从 `CryptoStream` 中读取明文：

```csharp
using var cryptoStream = new CryptoStream(
    fileStream,
    aes.CreateDecryptor(),
    CryptoStreamMode.Read);
```

写入模式的 `CryptoStream` 必须正常结束或释放，以便写入最后一个分组和 Padding；否则可能生成无法解密的文件。

### 2.2 Key、Salt 与 IV

AES 加密涉及三个容易混淆的概念：

- `Key`：AES对象中真正用于解密的key,长度为32位
- `Passward`自己设置的字符串密码,长度不固定,并不是真正用于解密的密码
- `Salt`：随机生成，无加密保存在文件开头。它和passward循环大量计算生成真正的32位密码。1、使密码32位标准化 2、增大试密码的难度（一次尝试需要循环计算数万次）
- `IV`：随机生成，无加密保存在文件开头，紧随Salt(当然也可以自己定义位置)。它的作用：使用key加密时，按块加密（16字节），明文与上一段密文异或后加密。初始上一段密文就是IV。所以它影响整个密文。所以当明文密钥都没变，加密后的内容也千差万别。


### 2.3 PBKDF2 密钥派生

用户输入的字符串通常不能直接作为 AES 密钥：长度不固定，而且可能容易被猜中。因此本包使用 `Rfc2898DeriveBytes` 实现 PBKDF2：

```csharp
using var derive = new Rfc2898DeriveBytes(
    password,
    salt,
    100000);

byte[] key = derive.GetBytes(32);
```

PBKDF2 根据以下内容派生固定长度密钥：

```text
Password + Salt + 迭代次数 + PRF -> 固定长度 Key
```

- `Password`：用户密码。
- `Salt`：每个文件随机生成。
- 迭代次数：本包使用 100000 次，增加暴力猜测每个密码的计算成本。
- `PRF`：PBKDF2 内部使用的伪随机函数。
- `GetBytes(32)`：派生 32 字节 AES 密钥。

加密和解密必须使用相同的 Salt、迭代次数、PRF 和输出长度，否则无法得到相同的密钥。

长期文件格式最好显式指定 PBKDF2 的哈希算法，并在文件头中保存格式版本和派生参数。否则将来调整算法或迭代次数时，旧文件可能无法读取。

### 2.4 SHA-256

SHA-256 是密码学哈希算法，可以把任意长度的数据映射为固定 256 bit，也就是 32 字节的摘要：

```text
任意长度数据 -> SHA-256 -> 32 字节 Hash
```

特点：

- 相同输入产生相同摘要。
- 输入发生微小变化，摘要通常会大幅变化。
- 很难从摘要反推出原始内容。
- 很难找到产生相同摘要的两个不同输入。

本包使用 SHA-256 检测文件是否发生变化：

```csharp
using SHA256 sha256 = SHA256.Create();
byte[] tag = sha256.ComputeHash(data);
```

流式计算可以避免把整个文件读入内存：

```csharp
byte[] tag = sha256.ComputeHash(stream);
```

但无密钥哈希只能发现损坏，不能防止主动篡改。攻击者修改数据后，也可以重新计算一个新的 SHA-256 摘要。

### 2.5 HMAC-SHA256

HMAC-SHA256 将 SHA-256 与密钥结合：

```text
Key + Data -> HMAC-SHA256 -> 32 字节 Tag
```

```csharp
using var hmac = new HMACSHA256(key);
byte[] tag = hmac.ComputeHash(data);
```

其结果同时依赖数据和密钥：

- 数据变化，Tag 会变化。
- 密钥变化，Tag 也会变化。
- 不知道密钥的一方难以为篡改后的数据生成有效 Tag。
- 写入和读取必须使用相同密钥。

因此：

- SHA-256 适合检测意外损坏。
- HMAC-SHA256 适合验证完整性和数据生成者是否持有密钥。
- 需要防篡改时应优先使用 HMAC-SHA256，而不是单独使用 SHA-256。

### 2.6 固定时间比较

验证 Tag 时不应直接使用普通数组比较。普通比较通常在遇到第一个不同字节时立即返回，运行时间可能泄露匹配前缀信息。

本包使用：

```csharp
bool valid = CryptographicOperations.FixedTimeEquals(
    calculatedTag,
    expectedTag);
```

固定时间比较用于降低时序攻击风险。比较前还应先验证 Tag 长度是否合法。

### 2.7 加密与认证的组合

AES 与 HMAC 的职责不同：

- AES：隐藏数据内容，提供机密性。
- HMAC-SHA256：验证数据是否被修改，提供完整性与认证。

本包采用先加密、再对密文计算 Tag 的顺序：

```text
写入：明文 -> AES 加密 -> 密文 -> HMAC -> Tag
读取：密文 -> 验证 HMAC -> AES 解密 -> 明文
```

读取时先校验密文，校验通过后才解密，这属于 Encrypt-then-MAC 思路，可以在解密前拒绝被篡改的数据。

当前受保护文件的布局为：

```text
[Tag][Salt][IV][Data]
```

- 未启用校验时不写入 `Tag`。
- 未启用加密时不写入 `Salt` 和 `IV`。
- 启用加密时 `Data` 是密文，否则是明文。
- HMAC Tag 覆盖 `Salt + IV + Data`，因此影响密钥派生、解密初始状态或明文内容的修改都会导致校验失败。

更完整的格式可以认证文件头与密文，并加入魔数、版本号、算法标识和密钥派生参数，便于安全升级和兼容旧文件。

### 2.8 安全边界

- 客户端程序中保存的密码和密钥最终可能被逆向提取。
- 本地加密可以隐藏文件内容并提高篡改成本，但不能把不可信客户端变成可信环境。
- 客户端加密不能替代服务端鉴权、权限控制和权威数据校验。
- 不要把 SHA-256 当作身份认证或防篡改方案。
- AES 只负责机密性，需要防篡改时应同时使用 HMAC。
